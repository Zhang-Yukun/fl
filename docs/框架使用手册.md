# 联邦学习框架使用手册

本文面向当前 `src/` 下的联邦学习实验框架，说明如何配置、运行、扩展和排查。内容以当前代码实现为准。

## 1. 框架定位

当前框架已经从“仅支持稀土价格预测”抽象为“联邦核心 + 任务插件”的结构：

在阅读本手册前，如果你需要先看通信语义、模型状态变化以及 protocol/oracle 评测口径，建议先读：[模型传输与评测流程说明](./模型传输与评测流程说明.md)、[默认传输语义数据流说明](./默认传输语义数据流说明.md)、[通信压缩文献对照表](./通信压缩文献对照表.md)。

- 联邦核心：负责客户端训练、服务器聚合、攻击评估、通信统计、结果保存、gRPC 多节点通信。
- 任务插件：负责模型构建、数据加载、损失函数、评估指标。

当前默认任务仍然是时序预测，默认模型是 vendored 的 `PatchTST`。

核心目录如下：

- `fedlab/entrypoints/`

- `fedlab/engine/`
  - `training.py`：本地训练、验证、测试、预测、攻击采样
- `fedlab/federated/`
  - `methods/`：联邦算法实现层，按 dense / sparse / quantized / encoded 拆分
  - `client.py`：客户端运行时，负责本地训练并把 payload 构建委托给方法对象
  - `server.py`：服务器运行时，负责聚合调度、验证测试、通信统计
  - `algorithms.py`：单机联邦主流程、攻击流程、异步攻击管理
- `fedlab/communication/`
  - `grpc_service.py`：gRPC 协议定义封装
  - `grpc_training.py`：多进程/多节点训练主流程
- `fedlab/security/`
  - `attacks.py`：DLG / iDLG 攻击实现与结果汇总
- `fedlab/utils/`
  - `config.py`：配置加载与 `--override`
  - `serialization.py`：模型参数序列化、按层筛选、trainable/untrainable 状态导出、量化、稀疏化
  - `aggregation.py`：聚合辅助逻辑
  - `artifacts.py`：配置/快照/结果保存
  - `tracking.py`：wandb 离线记录
  - `logging.py`：loguru 日志初始化
  - `privacy_accounting.py`：自适应裁剪 + RDP 隐私记账
- `configs/`：实验配置
- `scripts/`：运行脚本
- `tests/`：与模块结构对应的测试
- `docs/`：说明文档

## 3. 环境准备

在仓库根目录下，实际训练代码位于 `src/`。

## 5. 配置系统

### 5.1 基本规则

配置使用 YAML，支持 `includes` 继承和命令行覆盖。

例如：

```yaml
includes: fedavg.yaml

experiment:
  output_dir: outputs/qsgd

federated:
  algorithm: qsgd_fedavg
```

命令行覆盖示例：

```bash
python -m fedlab.entrypoints.train \
  --config configs/fedavg.yaml \
  --mode federated \
  --override experiment.output_dir=outputs/tmp_run \
  --override federated.rounds=100 \
  --override runtime.device=cuda:0
```

### 5.2 常用配置段

- `experiment`：实验名、模式、输出目录
- `runtime`：设备、随机种子、确定性、线程数、日志等级
- `task`：任务类型，当前默认 `forecasting`
- `data`：数据路径、客户端列表、窗口长度、batch size、shuffle、worker 数
- `model`：模型类型与结构参数
- `training`：学习率、优化器、早停参数等共享训练超参数；不再承载模式总轮数
- `centralized`：集中式专用训练轮数，例如 `centralized.rounds`
- `federated`：联邦算法、通信轮数、本地 epoch/step，以及当前算法真正会用到的传输参数
- `attack`：DLG/iDLG 攻击频率、步数、采样策略、异步参数
- `evaluation`：协议可见评测 or oracle 评测
- `tracking`：wandb 是否启用、是否离线
- `artifacts`：配置保存格式、周期性快照间隔
- 配置加载后会自动裁剪掉当前算法无关的算法块与 `federated` 扩展字段。
- `grpc`：多节点地址与轮询参数

## 6. 运行方式

### 6.1 集中式训练

直接调用入口：

```bash
cd src
python -m fedlab.entrypoints.train \
  --config configs/centralized.yaml \
  --mode centralized
```

### 6.2 单机顺序模拟联邦训练

直接调用入口：

```bash
python -m fedlab.entrypoints.train \
  --config configs/fedavg.yaml \
  --mode federated
```

### 6.3 多进程 / 多节点 gRPC 联邦训练

服务端：

```bash
python -m fedlab.entrypoints.server --config configs/fedavg.yaml
```

三个客户端：

```bash
python -m fedlab.entrypoints.client --client-id Nd2O3 --config configs/fedavg.yaml
python -m fedlab.entrypoints.client --client-id CeO2  --config configs/fedavg.yaml
python -m fedlab.entrypoints.client --client-id La2O3 --config configs/fedavg.yaml
```

若跨机器部署，只需保证：

- 服务端 `grpc.address` 对外可访问
- 各客户端的 `grpc.server_address` 指向服务器 IP:PORT
- 三端使用相同配置语义
- 客户端 `client-id` 与配置中的 `data.clients` 一致

## 7. 当前支持的算法

当前联邦算法由 `federated.algorithm` 控制。当前保留并维护的联邦方法名为：

- `fedavg`
- `adaptive_clipped_rdp_fedavg`
- `sparse_fedavg`
- `randomk_fedavg`
- `sign_fedavg`
- `qsgd_fedavg`
- `secure_quantized_fedavg`
- `ega_fedavg`

训练模式另有 `centralized`，它不走联邦方法注册表，而是走集中训练入口。

其中：

- `sparse_fedavg` 对应 Top-k 稀疏上传
- `randomk_fedavg` 对应 Random-k 稀疏上传
- `sign_fedavg` 对应 sign 压缩上传
- `qsgd_fedavg` 对应 QSGD 量化上传
- `secure_quantized_fedavg` 对应通用量化上传，常见 `quantization_dtype` 包括 `float16` 与 `qint8`
- `ega_fedavg` 对应编码上传

## 8. 训练、攻击、评测三条链路的当前语义

### 8.1 客户端默认上传什么

当前框架把每轮联邦语义拆成三层：

- `aggregation payload`：真正参与服务器聚合的上传内容
- `attack view`：服务器攻击端真实可见的内容
- `evaluation state`：仅在 oracle 评测时额外恢复的状态

默认联邦训练里，客户端上传给聚合器的是：

- `本地训练后模型参数 - 下发全局模型参数`

也就是 `update payload`，不是完整模型参数。

### 8.2 攻击默认看什么

服务器侧 DLG / iDLG 针对方法对象导出的 `attack view` 做攻击，也就是服务器在协议中真实看到的上传内容：

- dense 算法：dense update
- sparse 算法：可恢复的稠密 update 视图
- quantized 算法：反量化后的 update 视图
- encoded 算法：协议真正暴露给服务器的可解码视图

### 8.3 评测默认用什么

评测有两种模式：

- `evaluation.mode=protocol`
  - 默认模式
  - 服务器只用协议可见聚合结果做验证/测试
- `evaluation.mode=oracle_full_update`
  - 仅用于研究时比较协议路径与完整 dense 更新聚合路径
  - 客户端会额外上传 `evaluation_state`

因此默认模式下：

- `aggregation payload` 与 `attack view` 对齐真实协议
- `evaluation state` 默认为空
- 攻击与评测语义不会混淆

### 8.4 攻击何时发生、攻击谁、拿什么攻击

每轮顺序是：

1. 保存聚合前全局模型 `round_base_state`
2. 客户端基于该模型做本地训练
3. 客户端上传本轮更新 payload
4. 服务器完成聚合
5. 服务器在验证集上做本轮性能评估
6. 服务器构造攻击任务，并同步执行或异步排队执行攻击

攻击哪些客户端由这些配置控制：

- `attack.enabled`
- `attack.frequency_rounds`
- `attack.client_selection`
- `attack.clients_per_round`
- `attack.sample_count`
- `attack.max_samples`
- `attack.max_samples_cap`

### 8.5 当前攻击目标语义

当前代码只支持：

- `attack.target_type=update_payload`

也就是说服务器直接对协议中实际看到的客户端上传更新做攻击，不再提供独立的 `gradient` 模式。

### 8.6 DLG / iDLG 在本框架中的具体含义

当前每个攻击任务都会按配置顺序运行 `DLG` 与 `iDLG`：

- `DLG`：同时优化 `dummy_x` 和 `dummy_y`
- `iDLG`：
  - 分类任务下按原始 iDLG 论文的最后一层梯度符号逻辑推断伪标签，只优化 `dummy_x`
  - 时序 / 回归任务下退化为与 DLG 相同的目标优化形式

当前优化目标固定为 dummy batch 诱导出的一步近似本地更新与截获 `update_payload` 的差距。

### 8.7 攻击评估指标和成功判定

当前实现里，单次攻击至少会记录：

- `exact_target_mse`
- `nearest_client_train_mse`
- `matched_reference_indices`
- `matched_reference_metric_name`
- `matched_reference_metric_value`
- `recovered_count`
- `reconstructed_count`
- `reference_count`
- `budget_recovered_fraction`
- `coverage_recovered_fraction`
- `psnr`
- `ssim`
- `objective_mse`
- `iterations`
- `time_seconds`

当前默认主指标是 `budget_recovered_fraction`，含义是：

- `budget_recovered_fraction = recovered_count / reconstructed_count`
- `coverage_recovered_fraction = recovered_count / reference_count`

成功判定流程是：

1. 用 `attack.recovery_match_metric` 构造重构结果与参考集合之间的匹配矩阵
2. 用 `attack.recovery_match_objective` 决定匹配时越大越好还是越小越好
3. 用 `attack.recovery_success_metric` 与阈值判断样本是否恢复成功
4. 统计恢复率，并据此生成记录级与汇总级成功率

### 8.8 攻击产物保存位置

攻击相关结果主要落在：

- `attack_results.json`
- `attack_artifacts/`
- `summary.json`
- `saved_updates/`：服务器按攻击频率保存的客户端更新快照，供独立回放脚本读取

### 8.9 同步攻击、异步攻击与独立回放

同步攻击：当前轮训练结束后立即执行，主流程等待攻击完成。

异步攻击：当前轮只保存攻击任务快照，后台线程池执行，训练结束前统一收尾。

独立回放：`replay_saved_update_attacks.py` 会扫描 `saved_updates/`，按当前攻击配置重新执行 DLG / iDLG，输出格式与在线攻击保持一致。

### 8.10 攻击配置项对照表

下面这张表只列当前代码里实际读取的 `attack.*` 字段。

| 配置项 | 作用 | 常见取值 / 说明 |
| --- | --- | --- |
| `attack.enabled` | 是否启用攻击 | `true` / `false` |
| `attack.target_type` | 攻击目标类型 | 当前仅支持 `update_payload` |
| `attack.reference_metric` | 兼容旧字段，控制是否额外暴露部分参考指标 | `auto` / `reconstruction_mse` / `nearest_client_train_mse` |
| `attack.report_metrics` | 额外输出的攻击指标 | 默认 `auto` 仅暴露 `nearest_client_train_mse` |
| `attack.recovery_match_metric` | 构造样本匹配矩阵的指标 | `mse` / `psnr` / `ssim` |
| `attack.recovery_match_objective` | 匹配时目标方向 | `auto` / `min` / `max` |
| `attack.recovery_success_metric` | 判定样本恢复成功的指标 | `mse` / `psnr` / `ssim` |
| `attack.recovery_success_objective` | 恢复成功时目标方向 | `auto` / `min` / `max` |
| `attack.recovery_success_threshold` | 可选的恢复成功阈值 | 未设置时按成功指标的默认阈值推导 |
| `attack.frequency_rounds` | 攻击频率 | 每隔多少轮执行一次 |
| `attack.client_selection` | 客户端选择策略 | `all` / `first` / `round_robin` |
| `attack.clients_per_round` | 每轮攻击客户端数 | 对 `first` 和 `round_robin` 有效 |
| `attack.sample_count` | 每客户端每轮发起多少次独立攻击 | `auto` 时当前默认取 `1` |
| `attack.max_samples` | 单次攻击联合重构多少样本 | `auto` 时取客户端训练样本数 |
| `attack.max_samples_cap` | `attack.max_samples=auto` 时的上限 | 默认 `8` |
| `attack.steps` | 每次攻击的优化步数 | 越大越慢 |
| `attack.lr` | 攻击优化学习率 | 用于 dummy 变量优化 |
| `attack.optimizer` | 攻击优化器 | 当前仅支持 `adam` |
| `attack.restarts` | 重启次数 | 每次从新的随机初始化开始 |
| `attack.input_clip` | 对 `dummy_x` 做裁剪 | 常用于限制输入范围 |
| `attack.target_clip` | 对 DLG 的 `dummy_y` 做裁剪 | 仅在优化 `y` 时生效 |
| `attack.tv_weight` | 总变差正则权重 | 当前主要用于时序输入 |
| `attack.seed` | 攻击随机种子 | 控制重构初始化和异步 RNG 隔离后的可复现性 |
| `attack.model_mode` | 攻击时模型工作模式 | `train` / `eval` |
| `attack.local_optimizer` | `update_payload` 近似本地更新时假设的客户端优化器 | `adam` / `sgd` |
| `attack.local_lr` | `update_payload` 攻击中的本地学习率近似 | 默认回退到 `training.lr` |
| `attack.local_optimizer_eps` | `update_payload` 攻击中 Adam 近似的 `eps` | 默认 `1e-8` |
| `attack.success_mse_threshold` | MSE 口径默认阈值 | 仍用于默认恢复阈值推导 |
| `attack.success_ssim_threshold` | SSIM 口径默认阈值 | 仍用于默认恢复阈值推导 |
| `attack.success_rate_threshold` | 汇总层面的成功率参考阈值 | 用于 `summary.json` overall pass/fail 视图 |
| `attack.data_range` | PSNR / SSIM 的数据范围 | 归一化数据常取 `1.0` |
| `attack.async_enabled` | 是否启用异步攻击 | `true` / `false` |
| `attack.async_workers` | 异步攻击线程数 | 后台线程池 worker 数 |
| `attack.async_max_pending_rounds` | 异步攻击队列容量 | 队列满时主流程会等待空位 |
| `attack.device` | 攻击设备 | `cpu` / `cuda:0` / `same` 等；默认跟随 `runtime.device` |

## 10. 周期性保存与恢复

当前已支持按轮保存快照：

```yaml
artifacts:
  save_every_rounds: 10
```

快照目录会保存：

- 当时配置
- 当前模型
- 指标历史
- 攻击结果
- 摘要信息
- 必要的恢复状态

用途：

- 长实验中断后人工检查
- 中间结果留档
- 后续扩展自动恢复训练

## 12. 如何新增一个任务

如果后续要切到 CIFAR、ECG 或其他任务，不需要重写整个联邦核心，按下面接入。

### 12.1 需要实现什么

新增一个 `TaskSpec`，至少提供：

- `build_model(config)`
- `build_federated_loaders(config)`
- `create_loss(config)`
- `compute_metrics(pred, target)`

接口定义在：

- [base.py](../fedlab/tasks/base.py)

### 12.2 注册位置

在：

- [registry.py](../fedlab/tasks/registry.py)

把新任务加入 `_TASKS`。

### 12.3 推荐步骤

1. 新建 `fedlab/tasks/xxx.py`
2. 新建对应 dataset / model 模块
3. 在 `registry.py` 注册
4. 新增一个最小配置 `configs/xxx.yaml`
5. 增加 `tests/tasks/`、`tests/datasets/`、`tests/modeling/` 对应测试

## 13. 如何新增一个联邦算法

当前推荐按“方法模块 -> 配置 -> 脚本 -> 测试 -> 文档”的顺序接入，不再直接往 `client.py` / `server.py` / `algorithms.py` 里堆算法分支。

### 13.1 先确认算法属于哪一类

当前 `fedlab/federated/methods/` 按算法族拆分：

- `dense.py`：普通 dense update 类方法
- `sparse.py`：Top-k / Random-k / DP Top-k 等稀疏上传方法
- `quantized.py`：float16 / qint8 / sign / qsgd 等量化方法
- `encoded.py`：需要额外编码器上下文的方法

如果新算法和现有文件里的某一类语义接近，就继续放在同一类模块；如果语义明显不同，建议新增一个新的方法模块文件。

### 13.2 实现方法类

新增算法时，核心是实现一个 `FederatedMethod` 子类，接口定义在：

- [base.py](../fedlab/federated/methods/base.py)

通常需要实现或覆写这些接口：

1. `configure_client(client)`：客户端初始化附加状态
2. `configure_server(server)`：服务器初始化附加状态
3. `build_round_context(server)`：服务器每轮下发的算法上下文
4. `prepare_client_state(...)`：客户端本轮训练前如何解释下载状态
5. `client_update(...)`：客户端如何构建上传 payload
6. `aggregate(...)`：服务器如何聚合客户端结果
7. `extract_attack_payload(...)`：服务器攻击端真实看到什么

其中最关键的是后面三项，因为它们分别定义了：

- `aggregation payload`
- `evaluation state`
- `attack view`

这三层语义必须显式区分，避免压缩、攻击和性能评测串线。

### 13.3 注册算法

实现完方法类后，在对应模块上使用注册器：

- [registry.py](../fedlab/federated/methods/registry.py)

典型形式是：

```python
@federated_method(
    "my_method",
    compressed=True,
    description="Short summary",
)
class MyMethod(FederatedMethod):
    ...
```

运行时会通过 `build_method(name)` 自动构建方法实例，因此不需要再去主流程里补字符串分支。

### 13.4 什么时候需要改运行时

正常新增算法时，通常不需要修改下面这些运行时文件：

- [client.py](../fedlab/federated/client.py)
- [server.py](../fedlab/federated/server.py)
- [algorithms.py](../fedlab/federated/algorithms.py)

只有当你新增的是一种新的协议能力，而不是某个算法变体时，才需要动运行时。例如：

- 引入一种全新的多轮上下文广播机制
- 引入一种新的传输对象类型，现有 `ClientResult` 不足以表达
- 引入新的异步任务生命周期

如果只是换聚合规则、换上传压缩方式、换攻击可见视图，优先留在方法模块内部解决。

### 13.5 可直接复用的工具

新增算法时，优先复用这些公共能力：

- [serialization.py](../fedlab/utils/serialization.py)
  - 完整 / trainable / untrainable 状态导出
  - Top-k / Random-k 稀疏化与解压
  - 量化、反量化、按层筛选
- [aggregation.py](../fedlab/utils/aggregation.py)
  - 聚合辅助逻辑
- [privacy_accounting.py](../fedlab/utils/privacy_accounting.py)
  - 裁剪、加噪、RDP 记账

如果算法只是在现有 dense / sparse / quantized 路径上变化一点参数或聚合公式，优先在已有工具上组合，而不是再复制一套上传链路。

### 13.6 配置与脚本

建议每个算法新增：

- 一个独立配置文件 `configs/<algorithm>.yaml`
- 如有必要，再增加一个面向重复实验流程的 suite / wrapper 脚本

配置里至少要写清楚：

- `federated.algorithm`
- 算法自己的专属配置段
- 是否启用攻击、攻击频率与设备
- `evaluation.mode`

### 13.7 测试

至少补这些位置：

- `tests/federated/test_method_registry.py`
- `tests/federated/test_algorithms.py`
- `tests/federated/test_rawdata2_config_consistency.py`
- `tests/scripts/test_rawdata2_scripts.py`

如果改了序列化 / 量化 / 稀疏化，还应补：

- `tests/utils/test_serialization.py`

如果算法带有自己的数学约束或隐私记账逻辑，建议再单独建一个专门测试文件，例如：

- `tests/federated/test_my_method.py`

## 16. 常见扩展建议

### 16.1 做新任务时优先保持哪些边界

建议保持下面三层解耦：

1. 任务层：模型、数据、loss、metrics
2. 联邦层：本地训练、聚合、通信、攻击、评测
3. 运行层：单机顺序模拟 / gRPC 多节点

这样以后从时序换到图像，不需要重写联邦主流程。

### 16.2 做研究型算法时优先检查什么

优先检查四件事：

1. 上传 payload 是什么
2. 服务器攻击到底看到了什么
3. 服务器验证/测试到底用的是什么模型
4. 通信统计到底统计的是参数通信量还是实际传输量

这四件事如果不对齐，结果通常不可解释。
