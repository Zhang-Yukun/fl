# 联邦学习框架使用手册

本文面向当前 `src/` 下的联邦学习实验框架，说明如何配置、运行、扩展和排查。内容以当前代码实现为准。

## 1. 框架定位

当前框架已经从“仅支持稀土价格预测”抽象为“联邦核心 + 任务插件”的结构：

- 联邦核心：负责客户端训练、服务器聚合、攻击评估、通信统计、结果保存、gRPC 多节点通信。
- 任务插件：负责模型构建、数据加载、损失函数、评估指标。

当前默认任务仍然是时序预测，默认模型是 vendored 的 `PatchTST`。

## 2. 目录结构

核心目录如下：

- `fedlab/entrypoints/`
  - `train.py`：统一训练入口
  - `server.py`：gRPC 服务器入口
  - `client.py`：gRPC 客户端入口
- `fedlab/tasks/`
  - `base.py`：任务抽象 `TaskSpec`
  - `registry.py`：任务注册表
  - `forecasting.py`：当前时序预测任务实现
- `fedlab/datasets/`
  - `rare_earth.py`：稀土时序数据集与 dataloader 构建
- `fedlab/modeling/`
  - `forecasting.py`：模型构建逻辑
  - `reference_patchtst/`：拷贝进仓库的 PatchTST 参考实现
- `fedlab/engine/`
  - `training.py`：本地训练、验证、测试、预测、攻击采样
- `fedlab/federated/`
  - `methods/`：联邦算法实现层，按 dense / sparse / quantized / encoded 拆分
  - `client.py`：客户端运行时，负责本地训练并把 payload 构建委托给方法对象
  - `server.py`：服务器运行时，负责聚合调度、验证测试、通信统计
  - `algorithms.py`：单机联邦主流程、攻击流程、异步攻击管理
- `fedlab/communication/`
  - `grpc_service.py`：gRPC 协议定义封装
  - `grpc_training.py`：多进程/多节点训练主流程
- `fedlab/security/`
  - `attacks.py`：DLG / iDLG 攻击实现与结果汇总
- `fedlab/utils/`
  - `config.py`：配置加载与 `--override`
  - `serialization.py`：模型参数序列化、按层筛选、trainable/untrainable 状态导出、量化、稀疏化
  - `aggregation.py`：聚合辅助逻辑
  - `artifacts.py`：配置/快照/结果保存
  - `tracking.py`：wandb 离线记录
  - `logging.py`：loguru 日志初始化
  - `privacy_accounting.py`：自适应裁剪 + RDP 隐私记账
- `configs/`：实验配置
- `scripts/`：运行脚本
- `tests/`：与模块结构对应的测试
- `docs/`：说明文档

## 3. 环境准备

在仓库根目录下，实际训练代码位于 `src/`。

常用方式：

```bash
cd src
pip install -r requirements.txt
```

如果使用已有 `torch_env` 环境，直接激活后运行即可；当前脚本已经可以不依赖 `conda run`。

## 5. 配置系统

### 5.1 基本规则

配置使用 YAML，支持 `includes` 继承和命令行覆盖。

例如：

```yaml
includes: rawdata2_fedavg.yaml

experiment:
  output_dir: outputs/rawdata2_qsgd

federated:
  algorithm: qsgd_fedavg
```

命令行覆盖示例：

```bash
python -m fedlab.entrypoints.train \
  --config configs/rawdata2_fedavg.yaml \
  --mode federated \
  --override experiment.output_dir=outputs/tmp_run \
  --override federated.rounds=100 \
  --override runtime.device=cuda:0
```

### 5.2 常用配置段

- `experiment`：实验名、模式、输出目录
- `runtime`：设备、随机种子、确定性、线程数、日志等级
- `task`：任务类型，当前默认 `forecasting`
- `data`：数据路径、客户端列表、窗口长度、batch size、shuffle、worker 数
- `model`：模型类型与结构参数
- `training`：学习率、优化器、早停参数等共享训练超参数；不再承载模式总轮数
- `centralized`：集中式专用训练轮数，例如 `centralized.rounds`
- `federated`：联邦算法、通信轮数、本地 epoch/step，以及当前算法真正会用到的传输参数
- `attack`：DLG/iDLG 攻击频率、步数、采样策略、异步参数
- `evaluation`：协议可见评测 or oracle 评测
- `tracking`：wandb 是否启用、是否离线
- `artifacts`：配置保存格式、周期性快照间隔
- 配置加载后会自动裁剪掉当前算法无关的算法块与 `federated` 扩展字段。
- `grpc`：多节点地址与轮询参数

## 6. 运行方式

### 6.1 集中式训练

```bash
cd src
bash scripts/run_rawdata2_centralized.sh
```

或直接调用入口：

```bash
python -m fedlab.entrypoints.train \
  --config configs/rawdata2_fedavg.yaml \
  --mode centralized
```

### 6.2 单机顺序模拟联邦训练

```bash
bash scripts/run_rawdata2_fedavg.sh
```

等价入口：

```bash
python -m fedlab.entrypoints.train \
  --config configs/rawdata2_fedavg.yaml \
  --mode federated
```

### 6.3 多进程 / 多节点 gRPC 联邦训练

服务端：

```bash
python -m fedlab.entrypoints.server --config configs/rawdata2_fedavg.yaml
```

三个客户端：

```bash
python -m fedlab.entrypoints.client --client-id Nd2O3 --config configs/rawdata2_fedavg.yaml
python -m fedlab.entrypoints.client --client-id CeO2  --config configs/rawdata2_fedavg.yaml
python -m fedlab.entrypoints.client --client-id La2O3 --config configs/rawdata2_fedavg.yaml
```

若跨机器部署，只需保证：

- 服务端 `grpc.address` 对外可访问
- 各客户端的 `grpc.server_address` 指向服务器 IP:PORT
- 三端使用相同配置语义
- 客户端 `client-id` 与配置中的 `data.clients` 一致

## 7. 当前支持的算法

当前联邦算法由 `federated.algorithm` 控制。

### 7.1 基线与聚合类

| 算法名 | 说明 |
| --- | --- |
| `fedavg` | 标准 FedAvg，上传 dense update |
| `fedaware` | 自适应加权聚合基线 |
| `adaptive_clipped_rdp_fedavg` | 服务端自适应裁剪 + RDP 记账 |

### 7.2 压缩 / 量化类

| 算法名 | 说明 |
| --- | --- |
| `compressed_fedavg` / `sparse_fedavg` | Top-k 稀疏上传 |
| `randomk_fedavg` | Random-k 无偏稀疏上传 |
| `sign_fedavg` | Sign + mean-abs scale 压缩 |
| `qsgd_fedavg` | QSGD 风格多级随机量化 |
| `secure_quantized_fedavg` | 双向量化 FedAvg，支持 `float16` / `int8` 等 |

### 7.3 压缩 + 保护类

| 算法名 | 说明 |
| --- | --- |
| `dp_topk_fedavg` | 裁剪 + 噪声 + Top-k |
| `soteriafl` | 当前仓库中实现为 random-k + 本地 DP 的对比变体 |

说明：

- `fedpetuning` 已删除，不再属于当前框架。
- 不同算法的专属参数已经逐步拆到各自配置中；公共配置尽量只保留共有字段。

## 8. 训练、攻击、评测三条链路的当前语义

这是当前框架里最容易混淆的部分。

### 8.1 客户端默认上传什么

当前框架把每轮联邦语义显式拆成三层：

- `aggregation payload`：真正参与服务器聚合的上传内容
- `attack view`：服务器攻击端真实可见的内容
- `evaluation state`：仅在评测模式需要时额外恢复的状态

当前默认联邦训练里，客户端上传给聚合器的是：

- `本地训练后模型参数 - 下发全局模型参数`

也就是 `update payload`，不是完整模型参数。

### 8.2 攻击默认看什么

服务器侧 DLG / iDLG 默认针对“实际可见的上传负载”做攻击，也就是方法对象导出的 `attack view`：

- dense 算法：攻击 dense update
- 稀疏算法：攻击稀疏化后可重建的 update
- 量化算法：攻击反量化后的 update 视图
- 编码算法：攻击协议真正暴露给服务器的可解码视图

也就是说，攻击看到的是“协议里真的传了什么”，而不是直接从客户端模型内部偷看原始梯度。

### 8.3 评测默认用什么

评测有两种模式：

- `evaluation.mode=protocol`
  - 默认模式
  - 服务器只用协议可见的聚合结果做验证/测试
  - 客户端默认不会额外上传 `evaluation_state`
- `evaluation.mode=oracle_full_update`
  - 仅用于研究时比较“协议可见模型”和“完整 full update 聚合模型”
  - 客户端会额外上传 `evaluation_state`

因此，当前默认模式下：

- `aggregation payload` 与 `attack view` 对齐真实协议
- `evaluation state` 默认为空，不引入额外通信
- 攻击与评测语义不会混淆

### 8.4 攻击何时发生、攻击谁、拿什么攻击

当前框架里的攻击方默认是服务器，假设为 honest-but-curious server。

每轮的顺序是：

1. 服务器保存聚合前全局模型 `round_base_state`
2. 客户端基于该模型做本地训练
3. 客户端上传本轮更新 payload
4. 服务器完成聚合
5. 服务器在验证集上做本轮性能评估
6. 服务器构造攻击任务，并同步执行或异步排队执行攻击

因此：

- 攻击使用的是“本轮客户端上传之后、最终测试之前”的信息
- 攻击不会参与聚合
- 攻击不会改变本轮验证集指标

攻击哪些客户端由下面几个配置控制：

- `attack.enabled`：是否启用攻击
- `attack.frequency_rounds`：每隔多少轮做一次攻击
- `attack.client_selection`：`all` / `first` / `round_robin`
- `attack.clients_per_round`：每轮最多攻击多少个客户端
- `attack.sample_count`：每个被攻击客户端采多少个参考样本索引
- `attack.max_samples`：每次攻击实际截取的 batch 大小上限

当前正式实验主线里，常用的是：

- `attack.target_type=update_payload`
- `attack.client_selection=all`

这表示服务器直接对“协议中实际看到的客户端上传更新”做攻击。

### 8.5 两种攻击目标语义

当前支持两种攻击目标：

- `attack.target_type=update_payload`
- `attack.target_type=gradient`

`update_payload` 模式下：

- dense 算法：直接攻击客户端上传的 dense update
- sparse 算法：先把 `sparse_update` 解压回稠密 update 再攻击
- quantized 算法：先反量化回 float32 update 再攻击

这个模式更贴近当前联邦训练实际协议。

`gradient` 模式下：

- 服务器会从客户端训练集当前顺序中抽取指定 batch
- 基于 `round_base_state` 重新计算该 batch 的梯度
- 如果真实通信路径存在裁剪、加噪、量化或稀疏化，还会通过 `_protect_attack_gradients()` 做同口径近似

这个模式更贴近原始 DLG / iDLG 论文设定。

### 8.6 DLG / iDLG 在本框架中的具体含义

当前每个攻击样本都会分别运行两种方法：

- `DLG`：同时优化 `dummy_x` 和 `dummy_y`
- `iDLG`：只优化 `dummy_x`，`y` 固定为真实 `real_y`

两者共享同一类攻击循环配置：

- `attack.steps`
- `attack.lr`
- `attack.optimizer`
- `attack.restarts`
- `attack.lbfgs_history_size`
- `attack.input_clip`
- `attack.target_clip`
- `attack.tv_weight`
- `attack.seed`
- `attack.model_mode`

如果目标类型是 `gradient`，优化目标是 dummy batch 产生的梯度与截获梯度之间的差距。

如果目标类型是 `update_payload`，优化目标是 dummy batch 诱导出的一步近似本地更新与截获 update payload 之间的差距。

### 8.7 攻击评估指标和成功判定

当前实现里，每次攻击至少会记录：

- `reconstruction_mse`：重构输入与 `real_x` 的 MSE
- `exact_target_mse`：对指定真实样本的 MSE 视图
- `nearest_client_train_mse`：重构输入与该客户端训练集参考窗口最近邻的 MSE
- `psnr`
- `ssim`
- `gradient_mse`：优化目标残差
- `iterations`
- `time_seconds`

主指标由 `attack.reference_metric` 决定：

- `auto`：默认值
  - `gradient` 模式下等价于 `reconstruction_mse`
  - `update_payload` 模式下等价于 `nearest_client_train_mse`
- `reconstruction_mse`
- `nearest_client_train_mse`

成功判定规则：

- 先取主指标 `primary_mse`
- 若配置了 `attack.success_ssim_threshold` 且主指标是 `reconstruction_mse`，则还会联合考虑 SSIM
- 默认核心阈值是 `attack.success_mse_threshold`

因此当前 summary 里的：

- `attack_primary_metric`
- `attack_primary_metric_direction`
- `attack_overall_avg_mse`
- `attack_success_rate`

都应结合 `attack.reference_metric` 一起解释，不能脱离配置单独看。

### 8.8 攻击产物保存位置

攻击相关结果主要落在：

- `attack_results.json`：每次 DLG / iDLG 的标量记录
- `attack_artifacts/`：每次攻击的张量文件，通常包含 `real_x`、`real_y`、`reconstructed_x`，以及在可用时的 `reconstructed_y`
- `summary.json`：全局聚合后的攻击统计
- `metrics.json`：每轮训练指标，不直接保存完整攻击张量

如果启用了 wandb，还会额外记录：

- 每轮攻击统计
- 累计攻击成功率 / 平均 MSE
- 部分攻击重构可视化

### 8.9 同步攻击与异步攻击

同步攻击：

- 当前轮训练结束后立即执行攻击
- 主训练流程等待攻击完成

异步攻击：

- 当前轮只保存攻击任务快照
- 攻击任务进入线程池后台执行
- 主训练流程继续向后推进
- 训练结束前统一等待所有攻击任务收尾

异步攻击不会污染聚合和评测，因为攻击使用的是独立快照：

- `round_base_state` 的克隆
- payload 的克隆
- `real_x / real_y / reference_inputs` 的克隆

但异步攻击会竞争 GPU / CPU 资源，因此可能拉长 wall-clock 时间。

### 8.10 攻击配置项对照表

下面这张表只列当前代码里实际读取的 `attack.*` 字段。

| 配置项 | 作用 | 常见取值 / 说明 |
| --- | --- | --- |
| `attack.enabled` | 是否启用攻击 | `true` / `false` |
| `attack.target_type` | 攻击目标类型 | `update_payload` 或 `gradient` |
| `attack.reference_metric` | 主评估指标选择 | `auto` / `reconstruction_mse` / `nearest_client_train_mse` |
| `attack.frequency_rounds` | 攻击频率 | 每隔多少轮执行一次；实现上首轮和末轮也会攻击 |
| `attack.client_selection` | 客户端选择策略 | `all` / `first` / `round_robin` |
| `attack.clients_per_round` | 每轮攻击客户端数 | 对 `first` 和 `round_robin` 有效；`all` 时通常会攻击全部客户端 |
| `attack.sample_count` | 每个客户端攻击多少个样本索引 | 每个被攻击客户端会生成多少组攻击任务 |
| `attack.max_samples` | 单次攻击实际截取的 batch 大小上限 | 常用于把攻击 batch 限到 1 个或少数样本 |
| `attack.steps` | 每次攻击的优化步数 | 越大越慢，但重构可能更充分 |
| `attack.lr` | 攻击优化学习率 | 用于 DLG / iDLG 的 dummy 变量优化 |
| `attack.optimizer` | 攻击优化器 | `adam` / `lbfgs` / `sgd` |
| `attack.restarts` | 重启次数 | 每次从新的随机初始化开始，取最好结果 |
| `attack.lbfgs_history_size` | LBFGS 历史大小 | 仅 `optimizer=lbfgs` 时使用 |
| `attack.input_clip` | 对重构输入 `dummy_x` 做裁剪 | 通常用于限制输入范围 |
| `attack.target_clip` | 对 DLG 的 `dummy_y` 做裁剪 | 仅在优化 `y` 时生效 |
| `attack.tv_weight` | 输入总变差正则权重 | 当前主要对时序输入平滑性施加弱约束 |
| `attack.seed` | 攻击随机种子 | 控制重构初始化和异步攻击 RNG 隔离后的可复现性 |
| `attack.model_mode` | 攻击时模型工作模式 | `train` / `eval` |
| `attack.local_optimizer` | `update_payload` 攻击中近似本地更新的优化器假设 | `adam` / `sgd` |
| `attack.local_lr` | `update_payload` 攻击中的本地学习率近似 | 默认回退到 `training.lr` |
| `attack.local_optimizer_eps` | `update_payload` 攻击中 Adam 近似的 `eps` | 默认 `1e-8` |
| `attack.success_mse_threshold` | 主指标阈值 | `primary_mse <= threshold` 记为成功 |
| `attack.success_ssim_threshold` | 可选的 SSIM 成功阈值 | 仅在主指标为 `reconstruction_mse` 时参与成功判定 |
| `attack.success_rate_threshold` | 汇总层面的成功率参考阈值 | 用于 `summary.json` 中 overall pass/fail 视图，不是单次攻击优化阈值 |
| `attack.data_range` | PSNR / SSIM 的数据范围 | 归一化数据常取 `1.0` |
| `attack.async_enabled` | 是否启用异步攻击 | `true` / `false` |
| `attack.async_workers` | 异步攻击线程数 | 后台线程池 worker 数 |
| `attack.async_max_pending_rounds` | 异步攻击队列容量 | 队列满时主流程会等待空位 |
| `attack.device` | 攻击设备 | `cpu` / `cuda:0` / `same` 等；默认跟随 `runtime.device` |

使用建议：

- 想贴近真实联邦协议，优先用 `attack.target_type=update_payload`。
- 想贴近原始 DLG / iDLG 论文设定，优先用 `attack.target_type=gradient`。
- 想让结果可复现，至少同时固定 `runtime.seed`、`runtime.deterministic`、`attack.seed`，并控制训练集 shuffle。
- 如果异步攻击和训练共用一张 GPU，`attack.steps`、`attack.frequency_rounds`、`attack.async_workers` 三者需要一起权衡。

## 13. 如何新增一个联邦算法

当前推荐按“方法模块 -> 配置 -> 脚本 -> 测试 -> 文档”的顺序接入，不再直接往 `client.py` / `server.py` / `algorithms.py` 里堆算法分支。

### 13.1 先确认算法属于哪一类

当前 `fedlab/federated/methods/` 按算法族拆分：

- `dense.py`：普通 dense update 类方法
- `sparse.py`：Top-k / Random-k / DP Top-k 等稀疏上传方法
- `quantized.py`：float16 / qint8 / sign / qsgd 等量化方法
- `encoded.py`：需要额外编码器上下文的方法

如果新算法和现有文件里的某一类语义接近，就继续放在同一类模块；如果语义明显不同，建议新增一个新的方法模块文件。

### 13.2 实现方法类

新增算法时，核心是实现一个 `FederatedMethod` 子类，接口定义在：

- [base.py](../fedlab/federated/methods/base.py)

通常需要实现或覆写这些接口：

1. `configure_client(client)`：客户端初始化附加状态
2. `configure_server(server)`：服务器初始化附加状态
3. `build_round_context(server)`：服务器每轮下发的算法上下文
4. `prepare_client_state(...)`：客户端本轮训练前如何解释下载状态
5. `client_update(...)`：客户端如何构建上传 payload
6. `aggregate(...)`：服务器如何聚合客户端结果
7. `extract_attack_payload(...)`：服务器攻击端真实看到什么

其中最关键的是后面三项，因为它们分别定义了：

- `aggregation payload`
- `evaluation state`
- `attack view`

这三层语义必须显式区分，避免压缩、攻击和性能评测串线。

### 13.3 注册算法

实现完方法类后，在对应模块上使用注册器：

- [registry.py](../fedlab/federated/methods/registry.py)

典型形式是：

```python
@federated_method(
    "my_method",
    compressed=True,
    description="Short summary",
)
class MyMethod(FederatedMethod):
    ...
```

运行时会通过 `build_method(name)` 自动构建方法实例，因此不需要再去主流程里补字符串分支。

### 13.4 什么时候需要改运行时

正常新增算法时，通常不需要修改下面这些运行时文件：

- [client.py](../fedlab/federated/client.py)
- [server.py](../fedlab/federated/server.py)
- [algorithms.py](../fedlab/federated/algorithms.py)

只有当你新增的是一种新的协议能力，而不是某个算法变体时，才需要动运行时。例如：

- 引入一种全新的多轮上下文广播机制
- 引入一种新的传输对象类型，现有 `ClientResult` 不足以表达
- 引入新的异步任务生命周期

如果只是换聚合规则、换上传压缩方式、换攻击可见视图，优先留在方法模块内部解决。

### 13.5 可直接复用的工具

新增算法时，优先复用这些公共能力：

- [serialization.py](../fedlab/utils/serialization.py)
  - 完整 / trainable / untrainable 状态导出
  - Top-k / Random-k 稀疏化与解压
  - 量化、反量化、按层筛选
- [aggregation.py](../fedlab/utils/aggregation.py)
  - 聚合辅助逻辑
- [privacy_accounting.py](../fedlab/utils/privacy_accounting.py)
  - 裁剪、加噪、RDP 记账

如果算法只是在现有 dense / sparse / quantized 路径上变化一点参数或聚合公式，优先在已有工具上组合，而不是再复制一套上传链路。

### 13.6 配置与脚本

建议每个算法新增：

- 一个独立配置文件 `configs/rawdata2_xxx.yaml`
- 一个独立运行脚本 `scripts/run_rawdata2_xxx.sh`

配置里至少要写清楚：

- `federated.algorithm`
- 算法自己的专属配置段
- 是否启用攻击、攻击频率与设备
- `evaluation.mode`

### 13.7 测试

至少补这些位置：

- `tests/federated/test_method_registry.py`
- `tests/federated/test_algorithms.py`
- `tests/federated/test_rawdata2_config_consistency.py`
- `tests/scripts/test_rawdata2_scripts.py`

如果改了序列化 / 量化 / 稀疏化，还应补：

- `tests/utils/test_serialization.py`

如果算法带有自己的数学约束或隐私记账逻辑，建议再单独建一个专门测试文件，例如：

- `tests/federated/test_my_method.py`

## 16. 常见扩展建议

### 16.1 做新任务时优先保持哪些边界

建议保持下面三层解耦：

1. 任务层：模型、数据、loss、metrics
2. 联邦层：本地训练、聚合、通信、攻击、评测
3. 运行层：单机顺序模拟 / gRPC 多节点

这样以后从时序换到图像，不需要重写联邦主流程。

### 16.2 做研究型算法时优先检查什么

优先检查四件事：

1. 上传 payload 是什么
2. 服务器攻击到底看到了什么
3. 服务器验证/测试到底用的是什么模型
4. 通信统计到底统计的是参数通信量还是实际传输量

这四件事如果不对齐，结果通常不可解释。
