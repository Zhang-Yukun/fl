# 模型传输与评测流程说明

本文档说明当前框架中，非压缩与压缩联邦训练在“下发、客户端本地训练、上传、服务器聚合、协议评测、oracle 评测”各阶段的模型变化。内容以当前代码实现为准。

## 1. 适用范围

本文主要讨论单节点顺序模拟与本地联邦逻辑中的模型语义。gRPC 多节点在聚合和评测语义上保持一致，但目前 `download_mode=update` 仍未在 gRPC 路径中开放。

## 2. 符号表

下表中的不同符号有时指向同一份模型状态，只是处在不同阶段或代码变量名不同。

| 数学符号 | 含义 | 常见代码变量名 |
| --- | --- | --- |
| `G_r` | 第 `r` 轮开始时服务器保存的 protocol 全局模型 | `server.global_state`、`round_base_state` |
| `O_r` | 第 `r` 轮结束后服务器保存的 oracle 评测模型 | `server.oracle_global_state` |
| `C_{i,r}` | 客户端 `i` 在第 `r` 轮实际收到并用于训练的模型 | `received_global_state` |
| `L_{i,r}` | 客户端 `i` 在第 `r` 轮本地训练完成后的模型 | `local_state` |
| `U_{i,r}` | 客户端 `i` 在第 `r` 轮的精确本地更新，定义为 `L_{i,r} - C_{i,r}` | `subtract_state(local_state, received_global_state)` |
| `P^{down}_{i,r}` | 发给客户端 `i` 的下发 payload | `download_state` |
| `P^{up}_{i,r}` | 客户端 `i` 上传给服务器的聚合 payload | `aggregation_state` / `sparse_update` / `ega_payload` |
| `\hat{U}_{i,r}` | 服务器从上传 payload 解码后的协议可见更新 | `decompress / dequantize / decode` 后的 update |
| `E_{i,r}` | 仅供 oracle 评测的精确 dense evaluation update | `evaluation_state` |
| `B_r` | 服务器用于 protocol 聚合的基座模型 | `weighted_protocol_base_state(...)` |

### 2.1 两组常见等价关系

1. 在标准非压缩 FedAvg 中：
   - `C_{i,r} = G_r`
   - `B_r = G_r`

2. 在压缩下载或有损下载中：
   - `C_{i,r}` 不一定等于 `G_r`
   - `B_r` 也不一定等于 `G_r`
   - 此时必须显式区分“服务器保存的全局模型”和“客户端实际收到的模型”

## 3. 需要先区分的三条语义线

当前框架显式区分下面三类内容：

1. `aggregation payload`
   - 真正参与服务器聚合的上传内容。
2. `attack view`
   - 服务器攻击端真实可见的内容，从上传 payload 推导得到。
3. `evaluation state`
   - 只用于 `oracle_full_update` 评测的精确参考更新，不参与协议通信和协议聚合。

因此，压缩、攻击、评测在当前实现中不是同一个对象。

## 4. 非压缩流程

本节对应标准 dense FedAvg 风格，且默认认为：

- `upload_mode=update`
- `download_mode=model`
- 无上传压缩、无下载压缩

### 4.1 下发

服务器在第 `r` 轮开始时持有：

- `G_r`

对非压缩情形，客户端实际收到的模型就是：

- `C_{i,r} = G_r`

下发 payload 也是完整模型：

- `P^{down}_{i,r} = G_r`

### 4.2 客户端本地训练

客户端以 `C_{i,r}` 为初始模型做本地训练，得到：

- `L_{i,r}`

并构造精确本地更新：

- `U_{i,r} = L_{i,r} - C_{i,r}`

### 4.3 上传

非压缩时，客户端上传的是稠密更新：

- `P^{up}_{i,r} = U_{i,r}`

服务器看到的协议更新就是：

- `\hat{U}_{i,r} = U_{i,r}`

### 4.4 聚合

因为所有客户端都从同一个 `G_r` 开始训练，所以：

- `B_r = G_r`

服务器按样本数加权聚合：

- `G_{r+1} = B_r + \sum_i w_i \hat{U}_{i,r}`
- 也就是 `G_{r+1} = G_r + \sum_i w_i U_{i,r}`

这就是标准 FedAvg 的模型演化。

### 4.5 protocol 测试

验证和测试直接用：

- `server.global_state = G_{r+1}`

即：

- `protocol_val_model = G_{r+1}`
- `protocol_test_model = G_{r+1}`

### 4.6 oracle 测试

如果 `evaluation.mode=protocol`，则 `oracle` 退化为与 protocol 相同。

如果 `evaluation.mode=oracle_full_update`，则客户端会额外提交：

- `E_{i,r} = U_{i,r}`

服务器构造：

- `O_{r+1} = G_r + \sum_i w_i E_{i,r}`

对于非压缩 FedAvg，由于 `E_{i,r} = U_{i,r}` 且 `B_r = G_r`，所以：

- `O_{r+1} = G_{r+1}`

因此在非压缩精确场景中：

- `protocol model == oracle model`

## 5. 压缩流程

本节讨论压缩算法的一般情形，尤其是：

- 稀疏上传：Top-k / Random-k / SoteriaFL 风格
- 量化上传：float16 / int8 / sign / QSGD
- 编码上传：EGA
- 以及可能存在的有损下载

### 5.1 为什么压缩后不能再把所有状态都看成同一个模型

一旦某一侧存在有损压缩，就会出现下面几份不同但都合法的“模型”：

1. 服务器保存的 protocol 全局模型 `G_r`
2. 客户端真正收到并训练的模型 `C_{i,r}`
3. 服务器聚合时使用的 protocol base `B_r`
4. 服务器用于 oracle 评测的模型 `O_r`

在压缩场景中，它们通常不再两两相等。

### 5.2 下发

服务器先决定客户端理论上应该看到的目标模型 `target_received_state`，然后依据 `download_mode` 构造 payload。

#### 情形 A：`download_mode=model`

服务器下发模型本身：

- `P^{down}_{i,r} = target_received_state`

如果算法还对下载做了压缩，例如量化或 EGA 编码，则真正网络中发出的是：

- `Compress(P^{down}_{i,r})`

客户端收到后解压、反量化或解码，重建出：

- `C_{i,r} = Decode(Compress(P^{down}_{i,r}))`

若压缩无损，则 `C_{i,r} = target_received_state`；若有损，则 `C_{i,r}` 只是近似等于 `target_received_state`。

#### 情形 B：`download_mode=update`

服务器维护客户端上一次实际收到的模型 `C_{i,r-1}`，并下发相对它的更新：

- `P^{down}_{i,r} = target_received_state - C_{i,r-1}`

客户端收到并解码后得到更新近似值，再重建：

- `C_{i,r} = C_{i,r-1} + Decode(Compress(P^{down}_{i,r}))`

如果下载链路无损，则 `C_{i,r} = target_received_state`；如果下载链路有损，则 `C_{i,r}` 为压缩后客户端真实看到的模型。

### 5.3 客户端本地训练

无论下载是否压缩，客户端训练都基于自己真实收到的模型：

- 训练起点是 `C_{i,r}`，不是裸的 `G_r`

训练结束后得到：

- `L_{i,r}`

然后定义精确本地更新：

- `U_{i,r} = L_{i,r} - C_{i,r}`

这里的基准始终是“客户端本轮实际收到的模型”。

### 5.4 上传

客户端上传的不是 `L_{i,r}`，而是以 `U_{i,r}` 为基础的聚合 payload：

- `P^{up}_{i,r} = Compress(U_{i,r})`

不同算法的 `Compress` 形式不同：

- Top-k / Random-k：保留部分 trainable update 坐标；部分 buffer 可能 dense 上传
- `secure_quantized_fedavg`：对 dense update 做 float16 或 int8 量化
- `sign_fedavg`：上传符号与尺度信息
- `qsgd_fedavg`：上传 QSGD 级别量化后的 update
- `ega_fedavg`：对 trainable update 做编码，buffer 单独补充

### 5.5 服务器聚合

服务器拿到各客户端上传 payload 后，先恢复出协议可见更新：

- `\hat{U}_{i,r} = Decode(P^{up}_{i,r})`

这里的 `Decode` 可能是：

- 稀疏反解压
- 量化反量化
- EGA 解码

#### 关键点：聚合基座不是总等于 `G_r`

当前框架在压缩场景下会显式构造：

- `B_r = weighted_average(C_{i,r})`

也就是“各客户端这一轮实际看到并用于训练的模型”的加权平均。

这样做的原因是：

- 若下载是有损的，`C_{i,r}` 可能与 `G_r` 不同
- 服务器若仍直接用 `G_r` 作为聚合基座，会与客户端真实训练轨迹不一致

因此 protocol 路径的聚合公式是：

- `G_{r+1} = B_r + \sum_i w_i \hat{U}_{i,r}`

这比“直接在 `G_r` 上加平均更新”更贴合真实协议。

## 6. protocol 测试与 oracle 测试

### 6.1 protocol 测试

protocol 路径始终测试协议真实跑出来的模型：

- 验证时加载 `server.global_state`
- 测试时加载 `server.global_state`

即：

- `protocol_val_model = G_{r+1}`
- `protocol_test_model = G_{r+1}`

它反映的是：真实通信、真实压缩、真实解码、真实聚合之后的性能。

### 6.2 oracle 测试

如果启用 `evaluation.mode=oracle_full_update`，客户端还会单独构造：

- `E_{i,r}`

它通常是本轮的精确 dense 更新参考。服务器据此构造：

- `O_{r+1} = G_r + \sum_i w_i E_{i,r}`

注意这里有一个非常重要的实现语义：

- 当前框架中的 `oracle` 不是“从初始轮开始全程用 dense 精确更新重放的完整无损历史模型”
- 当前 `oracle` 是“以本轮 `round_base_state = G_r` 为基座，再叠加本轮精确 dense evaluation update 的评测参考模型”

因此在压缩场景下通常有：

- `O_{r+1} != G_{r+1}`

而且 `O_{r+1}` 也不一定等于“假设过去所有轮都无压缩时的完整理想轨迹终点”。

### 6.3 两者关系

- `protocol`：评估真实协议性能
- `oracle`：评估“若本轮上传载荷没有失真时”的参考性能

它们回答的问题不同，不能混读。

## 7. 攻击视图与评测状态的关系

服务器攻击默认基于上传 payload 的协议视图，而不是 oracle 状态。

也就是说：

- 攻击使用的是 `P^{up}_{i,r}` 能恢复出来的 `attack view`
- 不直接使用 `E_{i,r}`
- `E_{i,r}` 只为 oracle 评测服务

因此当前框架中：

- 聚合看到的是 `aggregation payload`
- 攻击看到的是 `attack view`
- 评测 oracle 用的是 `evaluation state`

三者是显式拆开的。

## 8. 两个常见特例

### 8.1 标准非压缩 FedAvg

通常满足：

- `C_{i,r} = G_r`
- `B_r = G_r`
- `\hat{U}_{i,r} = U_{i,r}`
- `O_{r+1} = G_{r+1}`

因此 protocol 与 oracle 完全一致。

### 8.2 稀疏 / 量化 / 编码压缩算法

通常满足：

- `C_{i,r}` 可能不等于 `G_r`
- `\hat{U}_{i,r}` 可能不等于 `U_{i,r}`
- `B_r` 可能不等于 `G_r`
- `O_{r+1}` 通常不同于 `G_{r+1}`

此时必须分别看：

- 真正训练轨迹：由 `C_{i,r}` 决定
- 真正聚合轨迹：由 `B_r` 与 `\hat{U}_{i,r}` 决定
- 真实协议性能：看 `G_{r+1}`
- oracle 参考性能：看 `O_{r+1}`

## 9. 推荐读法

如果目标是分析“模型是如何在协议里变化的”，建议按下面顺序读：

1. 先看 `G_r`、`C_{i,r}`、`U_{i,r}`、`B_r` 四个核心状态
2. 再看上传 payload `P^{up}_{i,r}` 是否对 `U_{i,r}` 做了失真
3. 再看 protocol 聚合得到的 `G_{r+1}`
4. 最后再看 oracle 评测得到的 `O_{r+1}`

如果目标是比较实验结果：

- 通信开销比较：优先看 `parameter_*` 和 `transport_*` 字段
- 真实性能比较：优先看 `protocol_val_*` / `protocol_test_*`
- 参考上限比较：再看 `oracle_val_*` / `oracle_test_*`
- 攻击风险比较：看 `attack_results.json` 与 `attack_summary`
