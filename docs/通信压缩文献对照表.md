# 通信压缩文献对照表

本文档整理几类常见通信压缩工作，重点说明：

- 压缩对象是梯度、更新量还是模型参数
- 主要压缩位置在上传、下发还是双向
- 与当前框架中已有算法的关系

## 1. 总体结论

从现有代表性工作看，通信压缩的主流仍然是 **上传压缩**，也就是客户端到服务器这一侧的梯度或更新量压缩。

更具体地说：

1. 经典梯度压缩工作大多讨论分布式 SGD 中的 worker 上传梯度压缩。
2. 迁移到联邦学习后，最自然的对象通常变成客户端上传的本地更新量或其近似。
3. 专门做下发压缩的工作存在，但数量明显少于上传压缩。
4. 同时系统性讨论上传和下发的工作，更多见于无线 FL、通信系统优化、或专门研究总通信量的论文。

## 3. 这些工作主要压缩在哪一侧

### 3.1 上传压缩主流

下面这些工作都更适合归到“上传压缩主流”里：

- QSGD
- signSGD
- signSGD with Majority Vote
- Deep Gradient Compression
- Sparsified SGD with Memory
- Error Feedback Fixes signSGD ...
- DAdaQuant

它们的共同特点是：

- 被压缩的对象主要是梯度或更新量
- 压缩动作主要发生在 worker/client 到 server 的链路上
- server 聚合后通常不强调再对下发链路做同等级别的理论设计

### 3.2 下发压缩是相对少数

DoCoFL 这类工作之所以值得单独拿出来，是因为它明确指出：

- 很多已有方法其实是为上传更新压缩设计的
- 这些方法未必适合直接搬到下发模型压缩上
- 下发压缩需要单独考虑客户端收到模型后的训练稳定性

### 3.3 双向压缩更多见于系统或无线视角

当论文把问题建模成“总通信开销最小化”或者“无线链路联合设计”时，就更容易同时研究：

- uplink compression
- downlink compression

但这类工作通常比纯上传压缩更复杂，也更偏系统问题。

## 4. 与当前框架已有算法的关系

下面是一个便于工程对齐的视图。

| 当前框架算法 | 更接近哪类文献路线 | 默认理解 |
| --- | --- | --- |
| `fedavg` | 无压缩基线 | 上传 dense update，下发 dense model 或 update 语义 |
| `sparse_fedavg` | Top-k 稀疏化 / Sparsified SGD 路线 | 主要对应上传稀疏 update |
| `randomk_fedavg` | Random-k 稀疏化路线 | 主要对应上传稀疏 update |
| `sign_fedavg` | signSGD 路线 | 主要对应上传 sign-compressed update |
| `qsgd_fedavg` | QSGD 路线 | 主要对应上传量化 update |
| `secure_quantized_fedavg` | 工程化量化变体 | 上传量化 update；框架里也支持下发侧量化语义 |
| `ega_fedavg` | 编码压缩路线 | 上传编码 update；框架里也支持下载编码语义 |

## 5. 对当前框架设计的启示

如果目标是与大多数压缩论文保持一致，最自然的路线是：

- 优先把上传当成主压缩位置
- 下发保持 dense 或仅做轻量低精度表示

如果目标是更真实地分析：

- 总通信量
- 压缩对训练轨迹的影响
- 压缩对攻击与评测语义的影响

那么就需要像当前框架这样，把上传和下发的语义都显式建模。
